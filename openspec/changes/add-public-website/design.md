# Design — public website and guide

## Architecture

Create `website/` as a separate React/TypeScript/Tailwind application using Next.js App Router and static export. This is a justified separate web dependency: unlike the existing authenticated Vite SPA, the marketing and guide pages need HTML in the initial response for indexing, direct links, and reliable previews. The site has no backend and uses no product API. Keep its package lock and build/deploy instructions within `website/`.

At build time, read Markdown from `../docs/user-guide` as the single content source. Enumerate only README and `NN-*.md` chapter files; derive stable `/docs` and `/docs/<slug>` paths. Render Markdown safely with GFM support and explicit link/image resolution. Reject path traversal, unknown local targets, broken fragments, and missing image alt text at build time. Copy or generate optimized guide images into the exported static output during build; do not check in duplicated screenshots. Treat `verity-user-guide.html` as a generated legacy artifact, not source content. Generate a compact search index from the same Markdown and search it client-side; the content pages remain static HTML.

Routes: `/` (marketing), `/demo` (request interface), `/docs` (guide index), `/docs/<chapter>` (13 chapters), and a not-found page. Static `sitemap.xml` and `robots.txt` enumerate public routes. Configure the canonical site origin at build time. Trial and sign-in use the existing app `/sign-up` and `/sign-in` paths at the user-provided `https://runwaydream.com` origin, overridable for staging. Both destinations were checked on 2026-10-01; verify them again before publishing.

The homepage embeds the demo form at `/#request-demo`; `/demo` remains a direct route to it. The form has full name, work email, company, optional context, preferred date, and preferred local-time window. Its calendar allows dates in the next 90 days; these are preferences, not available slots. No booking endpoint or inbox exists yet. Keep submit disabled and explain that no data is sent. Do not fabricate a success state, route personal data through a `mailto:` URL, or suggest a time is reserved. Connecting delivery later requires a reviewed service contract, privacy policy, abuse controls, and a live confirmation/availability path.

## Content and UX

Use the Verity product's neutral/sky palette and semantic approach from `docs/design-system.md`, but give the public site its own deliberate marketing typography, layout scale, and component styling. Create a text-first Verity wordmark or original owned mark. Do **not** copy `frontend/public/brand/app-mark.png`, which `brand-mark.tsx` identifies as a temporary Vimeo logo. Avoid competitor art, customer logos, certification badges, and fabricated numerical proof.

The v2 homepage follows a buyer's information path: (1) a short white introduction; (2) a light, left-aligned general GRC hero with trial and demo choices and an original animated relationship diagram; (3) a direct explanation of why cross-functional records matter; (4) capability overview; (5) alternating compliance, security, and third-party/risk sections with original example workspace views; (6) interactive relationship map; (7) tenancy, permissions, audit, and human-review details; (8) public documentation; (9) FAQ and the embedded demo preview form; (10) a light footer. The introduction plays once per session, can be skipped, and is omitted for reduced motion. The code-native diagram and product views are informed by actual workflows, not copied product screenshots or competitor assets. Example views identify themselves as such. Full product screenshots remain in the guide, where they help readers follow a task. Make the current SOC 2 content library explicit; additional framework content and business continuity are planned. VantageMDM is separate software, not a Verity integration. Do not imply fabricated customer metrics, endorsements, certification, or broad integration coverage. Use readable text and restrained motion with a no-motion fallback.

This structure adapts the readable header, broad platform menu, light hero, paced product demonstrations, and mobile patterns on [Harness](https://www.harness.io/). Its [documentation](https://developer.harness.io/artifact-registry/use-artifact-registry/manage-registries) informs the guide's clear chapter navigation, search, article width, and local contents. [Vanta](https://www.vanta.com/) and [Drata](https://drata.com/) inform general GRC positioning, while [Byro](https://byro.ee/) informs scroll rhythm and a spacious footer. Verity uses its own copy, data relationships, visuals, and brand. These are experience references, not sources for product claims or artwork.

Docs use role/task entry cards taken from guide README, a collapsible chapter sidebar, breadcrumb, local table of contents, readable article width, screenshot zoom/open behavior, and previous/next. Keep the guide's release notes prominent on the index and preserve notes within chapters. Treat images as documentation: retain descriptive alt text, provide dimensions, and let full screenshots be viewed without cropping. Search should index headings and body text, rank title/heading matches first, and link to the matching section where possible.

## Security and privacy

No browser access to repository paths or private files. Markdown rendering must not execute arbitrary HTML or JavaScript. Only local approved image assets and the declared app origin may be linked from content. The hosting layer should set a restrictive CSP, HSTS on HTTPS, Referrer-Policy, and `X-Content-Type-Options`; document a deployment example and a header smoke test. No cookies, analytics, live lead capture, or third-party script by default. Demo form values stay in the browser and are not persisted or sent. Links to the separate app do not carry tenant identifiers or session tokens.

## Failure, repeatability, and migration

There are no new tables, indexes, RLS policies, migrations, tenant-owned objects, or audit writes. Static generation is deterministic for the same guide source and build configuration; running it twice replaces the same generated output without changing platform data. Broken Markdown references, an absent public site origin, and unsupported content cause build failure with an actionable error. A slow or down app destination cannot delay page rendering because the site never calls it at runtime. No runtime external service or timeout is needed.

The deployment unit is the static export, with the repository root as build context so the guide source is available. A static host/CDN can serve it independently from the app; configure clean route fallback and headers. Production publication waits for the actual public domain, confirmation that `runwaydream.com` serves the app routes, and the booking service behind the demo request. Add approved legal/privacy links when personal data collection is enabled. Do not silently publish a nonfunctional booking CTA.

## Verification

Check exact chapter/image counts, all local links and fragments, and public route generation. Run typecheck, lint, production build, and focused tests for Markdown link resolution/search indexing. Inspect generated HTML for titles, canonical URLs and content; run accessibility checks and keyboard navigation on desktop/mobile; inspect responsive screenshots and actual guide images; verify reduced motion, performance budgets, no broken CTAs, and security headers on deployment. Manual copy review compares every capability claim with current code/user-guide status.
