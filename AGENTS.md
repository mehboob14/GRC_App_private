# Codex guide for Verity

Read [CLAUDE.md](CLAUDE.md) first. Then read the relevant [backend/CLAUDE.md](backend/CLAUDE.md), [frontend/CLAUDE.md](frontend/CLAUDE.md), [workflow](docs/conventions/workflow.md), [database conventions](docs/conventions/database.md), [data model](docs/architecture/data-model.md), and [ADRs](docs/adr/). These describe the intended design; check the current code, migration, and tests before relying on a claim. Preserve unrelated and uncommitted work.

## Current shape and change points

- `backend/src/verity/main.py` mounts versioned FastAPI routers. The backend is a modular monolith: `modules/<name>/` owns its router, schemas, models, and service; Week 1 modules also have repositories. Cross-module calls go through the owning service. `core/` owns configuration, authentication primitives, request dependencies, storage, and transactions; `db/migrations/versions/` owns schema changes and RLS policy DDL. Import boundaries are checked by `lint-imports`.
- `frontend/src/app/routes.tsx` composes the React SPA; `features/` contains feature pages and API calls, `lib/api/client.ts` the `/api/v1` bearer client, and `lib/auth/` the session. TanStack Query owns server state. `components/ui/` holds reusable primitives. API types are currently maintained by hand in `lib/api/types.ts` and feature `types.ts`; verify them against FastAPI schemas when changing a contract. Bearer tokens currently persist in `sessionStorage`, not an httpOnly cookie. The Vite dev proxy points to port 8001.
- `website/` is a separate static Next.js/React/Tailwind public site with no platform API or tenant session. Its documentation pages and branded screenshot copies are generated from `docs/user-guide/`; edit the source guide, not generated assets. Homepage product views are illustrative HTML/CSS examples, not captured app screens or live metrics. SOC 2 is the shipped framework library; do not market planned ISO content as live. See [website/README.md](website/README.md) for build and launch requirements. Demo booking is a non-submitting preview until a service is approved.
- PostgreSQL 16 uses one shared schema. `users`/`credentials` are global identities; `tenant_memberships` connects users to tenants. Platform admins are a separate population and login. Native password and TOTP auth is live; the external Keycloak-based IdP and SSO are deferred ([ADR-0006](docs/adr/0006-keycloak-as-identity-provider.md)). Authorization remains in Verity: `module:action` permissions, tenant roles and groups, active assignment windows, then any object scope.
- Global content and provider tables are distinct from tenant records. `backend/src/verity/seed/content/` and `verity.manage seed-content` supply SOC 2 controls, requirements, automation checks, questionnaires, risk and policy templates. `infra/docker/` runs Postgres, Redis, and MinIO; no Keycloak service. Celery beat and worker entry points are in `backend/src/verity/workers/`; the implemented schedules cover task SLAs, notifications, vendor and risk sweeps, vulnerability enrichment, and GitHub checks. Do not assume planned jobs or connectors already exist.
- Controls are the compliance hub: global framework/requirement/control-template content is adopted into tenant controls and requirement mappings. Evidence files are stored through `core/storage.py` (local by default, S3 compatible by configuration); metadata and hashes are in Postgres. `evidence_controls` maps evidence to controls, and requirement coverage follows the control-requirement map. Hot relationships use explicit joins; long-tail links use `linkage`. Vendor risk belongs to engagements and their lifecycle stages; assets anchor vulnerability instances; risk registers have their own scales. See [data model](docs/architecture/data-model.md) and the owning service before changing these relationships.
- The `approvals` package has no central implementation yet. Current document tiers, vendor decisions, evidence reviews, and risk acceptances live in their own modules. The GitHub connector is implemented; much of the wider connector catalogue and common-control-framework proposal remain planned. Treat OpenSpec checkboxes and old README text as historical context when code differs.

## Product UX to preserve

- This is an evidence-first B2B workbench. The intended journey is: Get Started shows real setup progress; an admin sees compliance posture while a member sees assigned work; module overviews expose gaps; searchable, filterable registers lead to record detail; detail tabs show proof, ownership, linked records, decisions, and history. A workflow should answer what needs attention, who owns it, what proves it, and what happens next. Read the relevant [user guide](docs/user-guide/README.md) alongside the screen code.
- Keep the repeated shell and interaction grammar: Overview / Compliance / Risk navigation; `PageHeader` and tabs for modules, `Toolbar` plus `Table` for registers, `DetailHeader` and tabs for records. Use existing `components/ui` primitives, semantic tokens, and the [design-system review checklist](docs/design-system.md#9-review-checklist). Dense data stays readable through hierarchy, not tiny text or decorative cards. Status words and colors are consistent and never color-only; severity is a separate scale. Use actionable loading, empty, filtered-empty, and error states. Prefer a drawer for a quick look, a modal for a focused decision, and a page for deep work; explain irreversible consequences before acting.
- Do not mistake a convincing screen for a live workflow. `dashboard/admin-dashboard.tsx` and `dashboard/my-day-dashboard.tsx` currently show hard-coded posture and task data, while `compliance/components/quick-start-page.tsx` reads live APIs but still calls connections a later-phase feature after GitHub shipped. The sidebar renders all configured modules even though the user guide says navigation is permission-filtered; backend permissions remain authoritative. Verify each screen's data source and access behavior before extending it, and label unavailable capabilities honestly.

## Invariants for any future change

1. Resolve the acting tenant from an authenticated membership (or a validated portal token), never a client-supplied tenant id. Tenant queries need explicit `tenant_id` filters **and** a transaction-local RLS binding via `get_tenant_session` or `session_scope(tenant_id)`. Provider visibility is privileged and uses `provider_session_scope`; never expose that switch to tenant input. Workers bind a fresh tenant transaction per unit of work. Do not commit inside a service: it discards the transaction-local setting.
2. Add `tenant_id`, appropriate FKs/uniques, tenant-leading composite indexes, grants, and forced RLS policies in the **same migration** as a new tenant table. Check that referenced IDs belong to the acting tenant; a foreign key to an ID alone does not establish tenant ownership. Use the app role without `BYPASSRLS` in isolation tests. Do not invent schema outside the approved data model/spec.
3. Keep all mutation audit entries in the same transaction as the change, with the right actor and before/after values. `audit_log` is append-only and its nullable `tenant_id` names the event stream. Respect the database append-only triggers/grants on history tables; do not hard-delete compliance records to hide history. Keep secrets encrypted before persistence and out of logs.
4. Enforce permissions in the backend route and object scope in the service; the UI is only a convenience gate. A cross-tenant or out-of-scope object should appear absent. Preserve the `error` versus `fail` distinction for connector checks. AI output and suggested evidence mappings are drafts until a human approves them.
5. Keep API request/response schemas and frontend types/callers aligned. Use the [design system](docs/design-system.md), `frontend/src/styles/ds-tokens.json`, and existing UI primitives; tenant accent is runtime data. Light mode is currently pinned in `frontend/src/lib/theme.tsx` despite dark token definitions. Preserve OpenLane policy-template attribution in `backend/src/verity/seed/content/policies/NOTICE.md` when changing shipped content.

## Working commands

From the repo root: `make setup`, `make up`, `make migrate`, `make run`, `make worker`, `make beat`, `make check`, `make test`, and `make test-isolation`. `make test` requires a reachable Postgres app role and sets `VERITY_REQUIRE_DB=1`; [local setup](docs/runbooks/local-setup.md) and [running the app](docs/runbooks/running-the-app.md) give Windows commands. `make run` binds the API to 8000, while the current Vite proxy and Windows runbook use 8001; match the ports before testing the UI. Frontend: `cd frontend; npm install; npm run dev`, `npm run typecheck`, `npm run lint`, `npm run build`. Backend CI checks format, Ruff, mypy, import boundaries, migrations, tests, and isolation; the workflow currently has no frontend job.

For feature work, follow [the spec and review workflow](docs/conventions/workflow.md): a schema, auth/tenant, dependency, connector, module-boundary, or API-contract change needs a reviewed spec first. Check the relevant OpenSpec change and ADR status; proposed features are not automatically implemented. Update affected docs with implementation. For a focused bug fix, start with a reproducing test. Do not change unrelated application behavior while documenting or investigating.
